# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

«Финишер — панель дня» — однопользовательская веб-панель ежедневника (Rust + axum, один HTML-файл),
электронная версия бумажного планера The Finisher's Journal. UI, комментарии в коде и данные — на русском;
новый код и комментарии писать так же.

## Commands

```bash
cargo run                       # dev-сервер на 127.0.0.1:8080
FINISHER_ADDR=0.0.0.0:8081 cargo run
FINISHER_DATA=/путь/к/state.yaml cargo run
cargo build --release
cargo check                     # быстрая проверка
```

Тестов в проекте нет — `cargo test` ничего не запускает.

`static/index.html` вшит в бинарник через `include_str!`, поэтому после правки фронтенда нужна
пересборка и перезапуск сервера (cargo отслеживает файл как зависимость, отдельного шага сборки нет).

## Architecture

Три файла несут всю систему: `src/main.rs` (71 строка), `static/index.html` (вёрстка + вся логика),
`data/finisher-data.yaml` (состояние).

**Сервер** — три роута, никакой доменной логики: `GET /` отдаёт вшитый HTML, `GET /api/state` возвращает
YAML-файл целиком (204, если файла нет), `PUT /api/state` проверяет только что тело — валидный YAML
и атомарно пишет его (tmp-файл + rename). Схема данных серверу неизвестна.

**Путь к данным по умолчанию зафиксирован на этапе компиляции** через `env!("CARGO_MANIFEST_DIR")` —
без переопределения бинарник пишет в `data/` того дерева исходников, где был собран, независимо от
рабочего каталога и места запуска (`WorkingDirectory=` в systemd на это не влияет, а `create_dir_all`
молча создаст каталог по зашитому пути, так что промах не даёт ошибки). Переменная `FINISHER_DATA`
задаёт путь в рантайме — использовать её при деплое, чтобы каталог сборки не был хранилищем данных.

**Фронтенд** — одно глобальное `state`, форму которого задаёт `defaultState()`. Привязка к DOM идёт
через атрибуты на элементах:

- `data-ed="путь.к.полю"` — contenteditable-текст, читается/пишется через `getPath`/`setPath`;
- `data-check="путь.к.полю"` — переключатель (класс `on`);
- `data-hcell="строка.индекс"` — клетка трекера привычек.

Делегированные слушатели `input`/`click` на `document` обрабатывают всё; отдельных обработчиков на
элементах нет. Добавить поле = добавить его в `defaultState()` и повесить `data-ed`/`data-check`
с нужным путём — рендер и сохранение подхватят автоматически.

**Дублирующиеся привязки.** Колонка 1 содержит вкладки-«закладки», повторяющие поля колонок 2 и 3
с теми же путями. Поэтому после правки вызывается `syncEd`/`syncCheck`, которые обновляют *все*
элементы с этим путём, кроме редактируемого. Ничего специального для новых дублей делать не нужно.

**Чтение YAML уже написанного, а не любого.** `dumpYAML` печатает валидный YAML — каждое значение
это `JSON.stringify`, а YAML надмножество JSON, — поэтому `serde_yaml` и любой сторонний парсер файл
прочитают. Обратная сторона, `parseYAML`, YAML-парсером не является: это построчный читатель ровно
того подмножества, что печатает `dumpYAML` (отступы для вложенности, `- ` для элементов, всё после
двоеточия идёт в `JSON.parse`). Обычные конструкции YAML он не переживает — некавыченные значения,
одинарные кавычки, комментарий в конце строки, блочные скаляры `|`, блочные маппинги внутри списка,
дата без кавычек дают SyntaxError, а ключ с отступленным многострочным текстом тихо превращается
в `{}`. Правя `data/finisher-data.yaml` руками, держаться формы, которую пишет `dumpYAML`.

**Сбой разбора выключает сохранение.** Если `parseYAML` упал, `load()` поднимает `loadFailed`, и
`scheduleSave()` больше не отправляет PUT, а показывает статус. Без этого пустая панель после сбоя
затирала бы файл дефолтами при первой же правке. Флаг ставится только на провал разбора: 204 на
первом запуске и недоступный сервер — отдельные ветки.

**Миграции.** `load()` делает `deepMerge` загруженного поверх дефолтов, затем `normalizeState()`
приводит старые сохранения к текущей форме (перестраивает `timeline` по часам, поднимает `mainEvent`
из строки в объект, добивает длины `dump`/`habits`). Меняя форму состояния, дописывать миграцию туда.

Сохранение — дебаунс 400 мс, PUT всего состояния целиком. Привычки хранятся строкой из 48 символов
`'0'`/`'1'` (12 месяцев × 4 клетки).

`fetch('api/state')` — относительный путь намеренно, чтобы приложение работало за прокси на подпути.

## Layout

Три колонки соответствуют страницам бумажного макета: стр. 7 (цель + закладки), стр. 32 (дневной
обзор), стр. 33 (тайм-бокс 5:00–20:00). Закладки в первой колонке переключают виды: цель, разгрузка
(30 строк), день недели, дневные задачи, трекер привычек.

`The Finisher's Journal — макеты страниц (RU).html` в корне — референс макетов бумажного журнала
(стр. 4–7, 10–11, 18–19, 32–35). Он не собирается и не отдаётся сервером; смотреть туда при переносе
новых страниц в панель.

## Deployment

Продакшен-схема: собранный бинарник под systemd слушает локальный порт, nginx проксирует на него
подпуть (`location /finisher/`). Поэтому фронтенд и ходит по относительному `api/state` — иначе
за прокси на подпути запросы уйдут в корень домена.

В юните обязательно задать `Environment=FINISHER_DATA=/абсолютный/путь/state.yaml`: иначе хранилищем
станет каталог, где шла сборка (см. про `CARGO_MANIFEST_DIR` выше), и данные потеряются при
пересборке в другом месте.
